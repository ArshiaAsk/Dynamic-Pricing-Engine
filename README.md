# Dynamic Pricing Engine

A demand-forecasting and price-optimization demo: an XGBoost model predicts demand
and a grid-search optimizer picks the price that maximizes expected revenue, served
through a FastAPI service with a Streamlit UI.

All data is **synthetic** (generated by `src/data/generator.py`); all metrics below
are measured on that synthetic data. This is a working demo, not a production system.

---

## Executive Summary

The Dynamic Pricing Engine combines machine learning for demand prediction with a
grid-search optimizer to maximize revenue while respecting business constraints
(margins, inventory, price ranges).

### What You Get

- 🤖 **ML Demand Forecasting**: XGBoost model predicting product demand (on synthetic data; R² 0.447 ± 0.029 / MAPE 0.361 ± 0.011 over data seeds 1–10, with the configured seed 42 as the reference run: R² 0.419 / MAPE 0.351 — see [Model Performance](#model-performance))
- 💰 **Price Optimization**: a `grid_search` optimizer that maximizes expected revenue under business constraints
- 🚀 **FastAPI Service**: REST API for pricing decisions, with Swagger/ReDoc
- 📊 **Health & Monitoring**: health/readiness/liveness checks, `/v1/metrics`, prediction logging
- 🐳 **Docker Deployment**: the image builds its own data + model
- 🔒 **Basic Hardening**: rate limiting (in-memory, per worker), input validation, generic error responses, container image runs as a non-root user and has a healthcheck
- 📈 **Operations Tools**: health-check, metrics and log-viewer shell scripts
- ✅ **Tested**: a pytest suite (unit + API contract + architecture) and offline-skipping smoke tests

## Core Features

### ML & Optimization
- **Demand Forecasting**: XGBoost-based model with a chronological train/validation split
- **Price Optimization**: a single `grid_search` method (alias `grid`) with business constraints
- **Feature Engineering**: automated calendar, price, and temporal features
- **Hyperparameter Tuning**: Optuna-based automated optimization (up to 50 trials)
- **Prediction Logging**: JSONL audit trail of API optimizations
- **Comprehensive Metrics**: MAE, RMSE, R², MAPE, directional accuracy

### Service Infrastructure
- **REST API**: FastAPI with automatic Swagger/ReDoc documentation
- **Monitoring**: Health checks, system metrics (CPU, memory, disk), request tracking
- **Logging**: Structured JSON logs, prediction audit trail (JSONL), log rotation
- **Containerization**: Docker (the image builds its own data + model)
- **Error Handling**: Global error handlers, input validation, graceful shutdown

### Deployment & Operations
- **Docker Compose**: one stack (`docker-compose.yml`) for the API and MLflow
- **Operations Tools**: health-check, metrics and log-viewer shell scripts

## Getting Started

### Prerequisites
- Python 3.12
- Docker & Docker Compose (for containerized deployment)
- Git

### Local Development Setup

```bash
# Clone repository
git clone <your-repo>
cd Dynamic-Pricing-Engine

# Create virtual environment
python -m venv venv
source venv/bin/activate  # On Windows: venv\Scripts\activate

# Install dependencies
pip install -r requirements.txt

# Configure (optional)
# Configuration lives in configs/config.yaml (single file; edit in place).
```

### Generate Data and Train the Model

A fresh clone has no data or model (both are gitignored). Generate the synthetic
dataset, then train — the full run takes a few seconds:

```bash
# Generate the synthetic dataset (50 products x 365 days = 18,250 rows)
python scripts/regenerate_data.py

# Train the model (writes models/demand_model.pkl, models/features.json, reports/)
python -m src.training.train

# Optional: train with Optuna hyperparameter tuning
python scripts/train_with_tuning.py

# Configuration options in configs/config.yaml:
# - run_cv: true       → Enable time-series cross-validation
# - tuning_trials: 50  → Number of Optuna tuning iterations
```

### Run API Locally

```bash
# Development mode (with auto-reload)
uvicorn src.api.server:app --reload --host 0.0.0.0 --port 8000

# Module form (no reload; used by scripts/verify_readme.sh)
python -m src.api.server

# Access API documentation
# - Swagger UI: http://localhost:8000/docs
# - ReDoc: http://localhost:8000/redoc
# - Health check: http://localhost:8000/v1/health
```

  and checks the API health response, that the process runs as a non-root user,

Local equivalents:

```bash

# The docker job (requires Docker)
bash scripts/docker_smoke.sh
```

## Model Performance

All data and metrics are **synthetic**. Across data seeds 1–10 the model's R² is
**0.447 ± 0.029** (range 0.406–0.500) and MAPE **0.361 ± 0.011** (range
0.347–0.380); the seed-to-seed spread is material. The configured seed 42 is
**the reference run** (`data.seed: 42`, 50 products × 365 days, 30 features,
chronological 80/20 split), recorded in `reports/training_metrics.json`;
regenerate it with the commands above.

Reference run (seed 42):

- **R² Score**: 0.419
- **MAPE**: 0.351
- **MAE**: 22.70
- **RMSE**: 30.97
- **Directional Accuracy**: 0.734

The served `grid_search` optimizer returns ≥ 0.99× the test-time reference optimum
across the optimizer test ranges, and for every seed in 1–10.

Feature importance: `reports/feature_importance.csv` (generated).

### How the model is served

Serving uses the **local artifact**: `models/demand_model.pkl` plus its feature
contract `models/features.json`. MLflow is used for experiment tracking and,
optionally, a registry — but a registry version must be **explicitly promoted**
(`scripts/promote_model.py`) before it is served. With no promoted production
alias, the engine logs the fallback loudly and serves the local artifact, which is
visible as `checks.model.source == "local"` on `/v1/health`.

## Limitations

- **The demand model is observational.** It is trained on historical price/demand
  pairs from the synthetic generator, not on controlled price experiments, so it
  learns the associations present in that data.
- **`argmax_price E[units | price]` is not a valid causal pricing policy on real
  data.** The model learns association, not causation: in real data prices are set
  in response to demand, competitors and inventory, so the estimated price response
  can be confounded, and a revenue-maximizing price derived from it can be wrong.
- **All results are on synthetic data.** Every metric describes how well the model
  learns the synthetic generator, not real-world accuracy.
- **Rate limiting is in-memory and per worker process.** Each process keeps its own
  sliding window; limits are not shared across workers and reset on restart.
- **No authentication, authorization or TLS.** The API is unauthenticated, serves
  plain HTTP, and CORS defaults to `*` (`src/api/server.py:50`).
- **The model artifact is a joblib pickle tied to the installed XGBoost version.**
  Loading an artifact produced by a different XGBoost version can warn or fail;
  retrain after upgrading the stack.
- **The MLflow registry is optional and requires explicit promotion.** With no
  promoted production alias the service falls back to the local pickle.
- **There is no drift monitoring and no automated retraining.** Drift detection and
  performance monitoring were removed (R15/D13); retraining is manual.

## Configuration

Edit `configs/config.yaml` (the single configuration file) for model, training and
feature settings:

```yaml
model:
  n_estimators: 600      # XGBoost trees
  max_depth: 6          # Tree depth
  learning_rate: 0.05   # Learning rate

pricing:
  price_min: 30.0
  price_max: 120.0

training:
  run_cv: false
  tuning_trials: 50
```
